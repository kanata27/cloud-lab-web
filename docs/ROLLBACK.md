# Откат и резервные копии

## Предпочтительный откат после полного переноса

Отключи автоматическую публикацию: repository variables `CLOUDFLARE_PRODUCTION_ENABLED=false`, `CLOUDFLARE_FULL_MIGRATION_READY=false`. Сохрани текущую D1 в `private/production-before-recovery.sql`:

```sh
npx wrangler d1 export EARNINGS_DB --remote --config wrangler.production.jsonc --output private/production-before-recovery.sql
```

Возвращай предыдущую рабочую **Cloudflare Access/D1-совместимую** версию Worker, оставляя D1 и Access на месте. В Cloudflare → Workers & Pages → kanata-web → Deployments → рабочая версия → Rollback. Откат кода не откатывает таблицы и записи. Верни соответствующий коммит в GitHub перед включением автодеплоя. Аналитическая миграция additive: не выполняй DROP TABLE в качестве отката интерфейса.

Если сломалась только политика входа, исправь Access/email/AUD; возвращать публичный доступ для ремонта не требуется. Рабочий главный сайт продолжает отдавать публичные файлы.

## Возврат на прежний AWS backend

Возможен только пока сохранены AWS-ресурсы и настройки. Это отдельный переход, а не безопасная кнопка общего отката: события и заработки, появившиеся после миграции, не копируются в AWS автоматически.

1. Сохрани актуальную D1 и все экспорты; не удаляй базу.
2. Убедись, что исправление текущего Worker/Access не решает проблему быстрее.
3. Если всё же возвращаешь старую версию, восстанови прежнюю настройку concurrency `kanata-analytics-api`: при ранее незаданной reserved concurrency удали ограничение, а при заданной верни точное старое число.
4. Убедись, что API Gateway и обе Lambda отвечают. Верни зафиксированную до миграции версию Worker и соответствующий исходный коммит с AWS API URL. Закрывающие Access-политики оставь. Старый Worker не содержит новой дополнительной проверки Access JWT, поэтому такой откат возвращает прежнюю модель защиты API; не используй его как окончательное решение.
5. Отчёты старого AWS API не включают новые D1-посещения. Для их обратного переноса нужен отдельный проверенный backfill, в этом пакете его нет. D1 остаётся источником этих данных. Не объявляй миграцию отменённой без сверки двух наборов.

Главный домен уже размещён в Workers; возврат DNS к старому ALB обычно не нужен и не является способом восстановить базу.

## Восстановление базы

До переключения сохранены SQL обеих D1, исходный и финальный DynamoDB JSON. Cloudflare D1 Time Travel имеет ограниченное окно восстановления (Free обычно 7 дней); не заменяет отдельную копию.

Восстановление всей D1 из дампа/Time Travel может стереть более новые заработки. Сначала экспортируй текущее состояние. Проверяй восстановление на отдельной временной базе и сверяй записи; подменять production базу без сверки не нужно. Обычная повторная загрузка `analytics-import.sql` безопаснее полной реставрации: она касается только baseline посещений и сохраняет live/earnings.

SQL с заработками — приватный файл, не GitHub artifact. Документация: [D1 backups](https://developers.cloudflare.com/d1/reference/time-travel/), [Worker rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).
